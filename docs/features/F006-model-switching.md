# F006 — Model Switching

## Priority: P0 (Core differentiator — one of three problems ChatGraph solves)

## Status: DONE

## Summary

Users can switch AI models at any point in the conversation. Each assistant node records which model generated it. The model selector is always visible, and switching models mid-conversation is seamless because OpenRouter accepts the full message history regardless of which model originally generated each response.

## Acceptance Criteria

- [x] Model selector dropdown visible in the UI (in graph panel or header)
- [x] Dropdown lists available models fetched from OpenRouter
- [x] Selecting a model changes it for the next completion request
- [x] Each assistant node stores the `model` field (e.g., "openai/gpt-4o")
- [x] Assistant nodes in the graph show a model badge
- [x] Model persists in UI state across node navigation (switching nodes doesn't reset model)
- [x] Users can create branches with different models from the same parent node

## Implementation Notes

- `ModelSelector.tsx` — searchable dropdown that opens upward from the message input area
- Models fetched via `GET /api/v1/models` which proxies to OpenRouter with 30-min server-side cache (`modelService.ts`)
- Default model: `openai/gpt-4o-mini` (stored in `uiStore.selectedModel`)
- `settingsStore.loadModels()` called on app init; model list stored in settingsStore
- Dropdown shows model name + pricing per token; limited to first 50 results for performance
- Provider grouping not yet implemented
- Context length warning not yet implemented

## How It Works

OpenRouter's API is model-agnostic for the message history. The `model` parameter only controls which model generates the **next** response. Prior messages are just `{ role, content }` — they don't carry model information.

This means:
```
Path: System → User → Assistant(GPT-4) → User → [next completion]
                                                     ↑
                                            model: "anthropic/claude-3.5-sonnet"
```
Claude will receive the full history including GPT-4's response, and generate the next reply. This is the core mechanic that makes model switching work.

## API

### `GET /api/v1/models`

Returns cached list of available OpenRouter models.

**Response:** `200`
```json
[
  {
    "id": "openai/gpt-4o",
    "name": "GPT-4o",
    "provider": "openai",
    "contextLength": 128000,
    "pricing": { "prompt": 2.5, "completion": 10.0 }
  },
  {
    "id": "anthropic/claude-3.5-sonnet",
    "name": "Claude 3.5 Sonnet",
    "provider": "anthropic",
    "contextLength": 200000,
    "pricing": { "prompt": 3.0, "completion": 15.0 }
  }
]
```

### OpenRouter Models Endpoint

```
GET https://openrouter.ai/api/v1/models
```

Returns all available models. Cache this server-side (refresh every 30 minutes).

## Model Comparison Use Case

A key workflow is comparing model responses:

1. User sends "Explain quantum computing" → gets GPT-4 response
2. User clicks the "Explain quantum computing" user node in the graph
3. Switches model to Claude
4. Sends the same message (or just triggers a new completion from that point)
5. Now two branches exist: one with GPT-4's answer, one with Claude's
6. User can visually compare them side by side in the graph

## Storage

- The `model` field on `Node` records the model used: `"openai/gpt-4o"`
- User nodes have `model = null` (they aren't generated by a model)
- System nodes have `model = null`
- The currently selected model is stored in `uiStore.selectedModel` (frontend only)
- Default model is stored in `Settings` table (persisted)

## Edge Cases

- **Model becomes unavailable**: If a previously used model is removed from OpenRouter, the node still shows it (historical data). New completions will fail with a clear error.
- **Context length exceeded**: Different models have different context windows. If the message path exceeds the selected model's context limit, show a warning before sending.
- **Auto model**: Support OpenRouter's `openrouter/auto` as a special option that auto-selects the best model.
